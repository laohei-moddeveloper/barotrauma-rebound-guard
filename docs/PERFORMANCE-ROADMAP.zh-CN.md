# 多人性能优化：根因、实施顺序与验收

2026-10-19。研究构建标识：`performance-foundations-20261019`。

本轮只考虑多人客户端、房主和实际服务器进程；单人游戏暂不纳入。
允许改动引擎、LuaCs 和网络内部实现，目标是降低真实帧时间、模拟延迟、卡顿和加载等待，保留可观察玩法。

## 先分清同样“卡”的不同原因

| 现象 | 根因候选 | 验证证据 |
| --- | --- | --- |
| 客户端掉帧 | 绘制提交、光照/粒子、驱动等待、主线程工作、GC | Draw 起点间隔，根 Update/Draw 和 GameScreen.Draw 分别计时；GPU 时间另测 |
| 全员动作变慢、输入滞后 | 实际服务器超过模拟预算、积压后丢输入 | 同局实际 server 的模拟步耗时、sim/wall、输入队列与裁剪 |
| 本机画面流畅但角色回弹 | 网络波动、状态发送排队、预测/权威状态不一致 | 输入确认与状态序列、RTT/抖动、排队年龄、受控角色最终画面位移 |
| 间歇性大卡顿 | 大量短命分配、LOH、GC、同步等待、任务调度 | 对应时间段和最坏步的阶段耗时、分配及 GC；重叠只说明相关 |
| 进局/换图/重载慢 | I/O、资源解析、C# 编译、动态补丁生成、逐 loader 等待和 GC | 分阶段墙钟耗时、线程 CPU/等待、程序集与原生资源的存活状态 |

一次停顿可能同时影响客户端、模拟追赶和网络队列。必须在同一局分别采集玩家和真正的服务器进程；房主客户端报告不能替代 server 报告。

## 重点一：本体减少重复工作和分配

优先定位物品、容器、状态效果、角色/AI、电力、水体、物理等阶段的累计耗时和尖峰。
对热点进一步分解调用次数、候选数量、对象分配和回退原因，再决定改算法还是数据布局。

已发现的具体研究入口：

- `NearbyItemIndex.RefreshTags` 为保持实时正确性，适用查询仍逐次扫描节点。先消除本来不必发生的查询、减少重复候选合并/排序，再评估连续数据和批量检查。不能只改成每帧审计一次：同一帧中的 Lua/C# 回调也能直接改 HashSet，普通方法 hook 还可能被 JIT 内联绕过。
- 公开源代码的更新循环有多个 `ToList()` 快照。若已审计运行时确认同样存在，研究按调用作用域复用快照容量；必须保留快照时刻、顺序、增删语义、重入和异常释放。不能直接改成遍历会变化的原始集合。大快照还可能进入 LOH。
- `ClientWriteIngame` 在每个实体位置序列化时创建临时消息。研究限定作用域的消息缓冲复用，并覆盖位位置、长度、调试标记、重入和异常路径。验收需要逐字节/逐位相同的包、相同 FIFO 与 MTU 行为；未经运行时验证，不直接替换消息对象。
- 绘制若成为瓶颈，分别研究可见对象筛选、光照/阴影工作、粒子和绘制批次。实际游戏绘制调用耗时仍可能包含驱动等待，不能用它冒充 GPU 执行时间。

源码依据包括仓库已有清单中的 FakeFishGames `e6e95da83b1b5ca8b55ec52653c7cf6b40e30247` 和 ProjectEP `2fcfcf6432cc42b34d10cb5fb4cff23ef57fd9fd`。
这些用于理解调用链，不代表与安装的 DLL 一致。例如 ProjectEP 公开更新循环含并行代码，不能把它直接当作已有方法指纹对应的运行时。所有引擎替换仍须核验实际方法。

### 已实施：附近查询按依赖失效

旧实现任意节点标签集合变化，就让所有查询的候选集合重新合并和排序。本轮分开了“物品列表结构变化”和“标签桶内容变化”：

- 物品增删/重排仍使相关结构整体失效，原生目标顺序不变。
- 标签变化只维护实际加入/移除的桶，保留未变的 prefab/标签桶。
- 每个变化的桶获得全局递增修订号。查询用相关现存桶的最大修订号和桶数量判断变化；数量不可省，否则删除非最大修订号的桶会被漏掉。删除后重新建立的桶取得更新修订号，不积累已删除标签的墓碑表。
- 全局没有新变化时直接复用候选；有变化时只检查该查询依赖的桶，相关依赖没变则不重做合并/排序。逐次真实标签审计、实时距离、IsValidTarget 和回退逻辑保留。
- 稠密回退会丢弃候选列表，因此显式标为未缓存，避免后续把已丢弃列表误当作“无目标”。新增 `candidate_rebuilds` / `candidate_reuses` 用于实战验证是否命中优化。

生产用 `BucketStamp` 已与独立的完整桶内容/顺序快照做 20,000 批变动对照，覆盖删除、重建和无关变化。实际 Barotrauma 查询结果、目标顺序及稠密回退新增检查已接入原生附近查询套件，仍待游戏宿主执行；没有声称完整查询或 FPS 已提高。

## 重点二：LuaCs 调用路径和加载路径同步优化

- 对真实模组组合统计高频 hook 的累计耗时、调用数、参数/结果转换和分配。现有 C# 回调包装基准不包含 Lua VM，不能代表完整 LuaCs 工作负载。
- 优先减少空工作、参数表/装箱、重复反射与重复生成；保留实时回调注册、顺序、ref/out、返回值、PreventExecution、异常和撤回行为。
- 本轮已去除同一桥接动态程序集上重复发射的访问许可属性。缓存只记录成功发射的许可，随 Context 重置；这减少生成期重复元数据，不宣称已经缩短完整加载时间。
- 研究替代“原工厂生成后，再生成额外桥接包装”的双重生成路径。要先审计完整原生成 IL 和服务生命周期，不能简单绕过原工厂。
- 原生移植按实际热点和源码审计推进，同时验证后加载 hook、重载、退出及 Lua 回退；不对未知规则统一硬替换。

## 重点三：实际服务器模拟与发送积压

本体的 `ClientWriteIngame` 主要先检查/入队，再出队发送。仅展示交错出入队的微基准不足以证明这里有收益。

本轮已实现：

1. 用出现次数维护 membership；出队时增量更新，正确处理重复项和 null。
2. 每个原生队列拥有自己的弱缓存，跨发送批次/客户端切换复用。仍检查 `_version`，外部 Clear、同数量替换等操作会触发重建。
3. 每次发送结束（含异常）释放快速访问对；回合结束和插件清理时释放缓存。弱键本身不能解决“原生队列跨回合仍存活”的引用保留，因此必须有回合清理。
4. 保留原生 FIFO、包预算和丢弃策略。没有启用位置投影或改动输入裁剪政策。

继续补排队年龄和端到端确认延迟，区分 CPU 算不过来、带宽/发送预算和传输抖动。队列长度和纠正分支计数都不能直接当作可见回弹。

## 重点四：多核调度按完整阶段收益验收

先核验当前引擎和第三方补丁已有的并行，再研究任务粒度、线程争用、嵌套调度和屏障。
worker 数要对照 1/2/4 等配置，不能认为 CPU 使用率更高就是更快。

- 独立、只读或写入互不重叠的数据准备优先。
- 共享 AI、Lua VM、水体、电力和物理写入必须建立真实依赖与合并顺序。
- 核心物理求解不仅验证位置/速度，也验证碰撞回调、关节、生成删除、连续世界与 TOI。
- 现有初始化局部加速尚未带来稳定的完整物理步收益，因此有序共享速度求解继续保持关闭。

## 重点五：加载和卸载生命周期

分别测冷启动、首次进局、换图、加入中途游戏、重载和退出。逐 loader 记录编译、补丁生成、操作计数等待和 GC，而不是只有一个总时间。

研究在正确生命周期屏障处合并重复 GC/等待。需要证明 collectible ALC、原生库、回调、后台任务和临时引用的释放顺序；不能简单删除 GC 或缩短等待来掩盖仍在使用的资源。
已有提前结束枚举的两秒等待修复仍保留，但它不证明所有加载慢都已解决。

## 本轮已完成的测量与可运行检查

- 多人客户端新增根 Update、根 Draw 和 GameScreen.Draw 的只读计时，以及 Draw 起点间隔和单次根 Update 内的模拟步数。
- 只采集前台、未暂停、非加载画面的多人游戏。转换会断开帧间隔连续性；首次 Draw 不制造虚假间隔。当前根 Update/Draw 尚未完成的样本留到下个报告窗口。
- 所有调用耗时是包含等待的墙钟时间。根 Draw 可能包含限帧等待；没有 GPU 时间戳，也不把根 Draw 当作纯绘制时间。
- 报告分析将帧、模拟、最坏步子系统、GC、受控角色纠正、Lua 桥接和服务端积压保留在对应窗口，支持旧报告和截断尾部。不把窗口均值 p95 当作逐帧 p95，不把嵌套分配相加，不从同窗重叠推导因果。
- 构建标识进入启动/环境日志，便于区分发布 0.4.0 和研究分支。旧验证 JSON 与发布清单不改写成新验证。

云端 Debian / .NET 8.0.32，Release，关闭分层 JIT。当前可移植检查：109,749 项队列断言、11 项帧统计检查、143,780 项依赖失效比较和 7 个 Python 报告分析测试。大量断言是循环中的状态比较，不是独立游戏场景数。

一次合成基准结果，单位为完成整个 fixture 的 ms。发送 fixture 每次 24 批，每批扫描指定数量候选后发送 16 项；包含初始化。不包含真实实体序列化或网络传输。

## 尚未完成的验收

云端没有已审计的游戏 DLL、Windows 游戏自带运行时、真实潜艇存档或联机进程。因此没有完成整包 Client/Server 编译、Harmony 实际挂接、LuaCs 元数据检查、包字节对照、真实绘制或联机 A/B。可移植测试也不替代这些检查。

同一组队列/帧统计/依赖修订测试已接入 `Verify-Deep.ps1`；新增附近查询结果/缓存复用、桥接许可/重置和客户端帧 hook 生命周期检查也需要在实际游戏宿主执行。

```powershell
pwsh -NoProfile -File tools/Verify.ps1 -GameDir 'ACTUAL_GAME_DIR' -Side Client
pwsh -NoProfile -File tools/Verify-Deep.ps1 -GameDir 'ACTUAL_GAME_DIR' -Side Client
pwsh -NoProfile -File tools/Verify-Deep.ps1 -GameDir 'ACTUAL_GAME_DIR' -Side Server
```

实战比较至少区分：旧发布版、同诊断配置的旧算法基线、本轮构建；固定存档/潜艇/模组、人数、战斗步骤、画质和限帧，交替运行，预热后采集多轮。
看真实帧间隔 p95/p99、超过 50 ms 的停顿、服务器 sim/wall、输入丢弃、确认/队列年龄、可见回弹与加载分阶段耗时，同时检查玩法状态、回调和数据包一致性。

本轮是已实现并完成部分验证的研究增量，不是解决全部多人卡顿的正式发布。下一处引擎改动应由上述实测中占用最大的具体调用链决定。
